# Supplied audit history

`poe audit-seed-large` loads a large audit history into the `audit_events` table of the
running stack, and `poe verify` loads the same history into a database of its own. This
directory holds the two pieces of it that are written out by hand.

| File | What it holds |
|---|---|
| `sample-trails.json` | Five sample exceptions and the history position of each of their events. The first is the measurement exception, `exc-5c2e8f14-7a3b-5d91-b6e0-4f8a2c9d1e37`: every Task 4.9 measurement uses its trail |
| `trail-baseline.json` | The stored baseline: each sample exception's trail as the supplied `trail_for_exception` returns it, oldest first, ties broken by the table's sequence. `poe audit-trail-compare` and `poe verify` compare your query's trails with it, event by event |

Everything else in the history is generated by `src/api/audit_history.py` from its position
alone: 300,000 events in all, for 25,000 filler exceptions and the five samples, spread so
that one exception's events lie far apart in the table. The generator and these two files
are deterministic, so every load writes the same rows in the same order.

## Synthetic

Every event, exception id, reading id, shipment, site, trace id, digest and dispatcher name
here is invented. No event describes a real shipment, clinic, person or system. Every
exception id is `exc-` followed by a lower-case UUID, as the ids the API mints are.

## Provenance

Authored for Task 4.9 on 2026-10-06. The sample trails were written by hand to include a
redelivery, a late-arriving read whose trail order differs from its load order, and reads
recorded in the same second; the baseline orders them as the supplied query does. A unit
test (`tests/unit/api/test_audit_history.py`) recomputes that order from
`sample-trails.json` and requires the baseline to match it.
